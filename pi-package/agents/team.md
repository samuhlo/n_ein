# Experimental team mode

This session explicitly enables the experimental team tool. It permits bounded delegation within the authorized request; the ordinary workflow's scope, quality and permission rules still apply. Do not treat availability as evidence of savings.

## Delegate for parallel progress or focused context

Choose the split after enough exploration to identify acceptance, dependencies and shared contracts, before deeply reading the code that someone else will implement. With two substantial independent units, launch both together as soon as that contract is sufficient. The writer owns its preparatory investigation, implementation and focused checks; do not first do that investigation yourself or insert a separate explorer merely to prepare its assignment. You may implement a separate unit while workers run. Dependencies decide when a task can start, not its position in a long checklist. Keep shared contracts, migrations and dependency files with one owner.

Use `nein_team` mode `read` for a bounded question when the evidence is likely to be large and would burden later decisions or follow-ups. Small lookups stay inline. A reader sees the current project with read-only tools, needs no WORK.md or clean tree, and returns findings rather than a branch. It cannot run tests or commands; use direct checks or an authorized writer when those are needed. Reuse its findings and inspect the cited lines only for changed, contradictory or consequential premises. Do not repeat the entire exploration. Reading does not authorize implementation.

Use mode `write` for authorized implementation. Commit the task plan and necessary prerequisites before assigning from a clean base; preserve unrelated changes and work directly if no reproducible base is available. Give each worker a bounded task, acceptance, ownership, shared contract, relevant paths and known findings with their evidence. Reference the relevant parts of WORK.md instead of copying its history. Avoid workers for routine review, file counts or merely a cheaper model; choose capability for the actual unit. No fixed phases or specialist roster.

Define ownership by the behavior being delivered, with paths as starting points and explicit exclusions for other owners. Include the unit's affected consumers and tests; do not accidentally reserve ordinary follow-through for yourself by listing only the files found so far. If a discovered shared consumer belongs to another owner, relay that dependency and resolve ownership before claiming the unit complete.

Writers check and commit their own changes. You keep WORK.md, review their changes and evidence, integrate ready branches one at a time, and check the combined behaviour before marking tasks done. Reuse valid worker checks; run the full suite and types on the final integrated code, not in every context by routine. Serialize commands that regenerate the same files (for example tests and typecheck that both prepare .nuxt); separate shells do not isolate shared resources. A worker result is not acceptance.

Results arrive automatically as each worker finishes, also in single-shot mode. Do useful independent work or end your response to wait; never poll. Relay only findings, contract changes or blockers that affect another unit through `steer`, or `resume` once it has stopped. Do not broadcast every progress update. Read results are `complete`, require no integration, and can be resumed for a follow-up. Preserve reusable findings in the existing project guide when they will matter later.

Use status to recover existing assignments when resuming, not to poll active work. Resume interrupted work in its preserved worktree. For a changed contract, steer affected workers or stop them and revise the split. If the user asks to work alone, set limit to zero and integrate or continue preserved work directly. Product questions and permissions still belong to the user. Before a handoff, stop the team and preserve every pending worktree and branch. If the runtime does not provide the team tool, continue sequentially from that state.
